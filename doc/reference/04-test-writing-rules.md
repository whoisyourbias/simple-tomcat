# 테스트 작성 규칙

이 규칙은 `src/test/java/`의 모든 테스트와 앞으로 추가할 테스트에 적용한다. JUnit Jupiter를 사용하며, 검증 목적과 실패 원인을 코드만 읽고 이해할 수 있게 작성한다.

## 검증 목적 주석

- 모든 테스트 메서드의 첫 테스트 애너테이션 바로 위에 한국어 설명 주석을 작성한다. 기본 형식은 `/** ... */`로 통일한다.
- 어떤 입력·상황에서 어떤 결과를 검증하는지 적는다. 상태 코드·예외·호출 횟수·상태 보존·종료 여부 등 실제 판정 기준을 구체적으로 쓴다.
- `@Test`뿐 아니라 `@ParameterizedTest`, `@RepeatedTest`, `@TestFactory`, `@TestTemplate` 등 테스트 실행 진입점에도 적용한다. 동적 테스트는 생성 메서드의 주석과 개별 테스트 이름으로 각 검증 목적을 드러낸다.
- 매개변수화 테스트는 입력들이 대표하는 조건과 공통 기대 결과를 설명한다. 서로 다른 기대 결과라면 테스트를 나누거나 각 입력과 기대 결과의 관계를 명확히 표현한다.
- 메서드 이름·`@DisplayName`·Given/When/Then 표지만으로 검증 목적 주석을 대신하지 않는다.
- 주석은 assertion이 실제 확인하는 범위만 설명한다. 객체에서 상태 값을 조회하는 테스트를 실제 HTTP 전송까지 검증한다고 쓰지 않는다.
- 여러 assertion이 한 동작을 확인한다면 주요 관찰 결과를 함께 설명한다. 독립적인 동작은 새 테스트 작성 시 메서드를 나눈다.
- 테스트 변경 시 주석도 갱신한다. 보조 메서드·테스트 서버에는 대기·종료 등 코드만으로 이유를 알기 어려운 부분을 설명한다.

예시:

```java
/** 한글 다섯 글자와 LF를 본문으로 설정하면 UTF-8 기준 16바이트로 저장하는지 검증한다. */
@Test
void measuresBodyInUtf8Bytes() {
    Response response = new Response();

    response.setBody("안녕하세요\n");

    assertEquals(16, response.getBody().length);
}
```

위 코드는 주석 위치와 준비·실행·검증 순서의 예시다. 실제 테스트에는 대상 클래스와 JUnit의 import도 포함한다.

## 이름과 구성

- 테스트 클래스는 대상 클래스에 대응하는 `대상Test`로 이름 짓는다. 단위 테스트는 대상과 같은 패키지, 실제 연결을 사용하는 통합 테스트는 `simpletomcat.integration`에 둔다.
- 메서드 이름은 조건과 기대 동작이 드러나는 영어 lowerCamelCase로 쓴다. `test1`, `works` 같은 이름은 피한다.
- 새 테스트는 준비 → 실행 → 검증 순서로 읽히게 작성한다. 각 구역은 필요하면 빈 줄로 나누고, 짧은 테스트에 형식만 맞추는 구역 주석을 반복하지 않는다.
- 각 테스트는 독립적으로 실행할 수 있어야 한다. 실행 순서, 다른 테스트의 상태, 외부 서버에 의존하지 않는다.
- 같은 계약을 입력만 바꾸어 확인할 때는 매개변수화 테스트를 사용한다. 보조 메서드는 요청 생성·응답 분리·서버 정리 등 반복되는 작업을 묶되 핵심 기대 결과를 숨기지 않는다.

## 검증 대상과 assertion

- 공개 계약과 관찰 가능한 동작을 검증한다. private 구현이나 자료구조를 그대로 따라가는 테스트보다 반환 값·전달 데이터·호출 순서·응답·생명주기를 확인한다.
- 정상 경로와 함께 변경에 관련된 오류·경계 조건을 다룬다. 요청 형식 오류, 빈 값, 중복 값, 미지원 기능, 예외, 상태 초기화 등이 해당한다.
- 요청 거부 시 필요하면 Adapter 호출 0회도 확인한다. 오류 격리가 요구되는 변경은 오류 응답과 다음 정상 연결 처리를 함께 검증한다.
- 바이트 기반 프로토콜에서는 문자 수와 바이트 수를 구분한다. 인코딩을 명시하고 한글 등 다중 바이트 입력으로 길이·본문을 확인한다.
- 결과 값은 `assertEquals`·`assertArrayEquals`, 예외는 `assertThrows`, 인스턴스 동일성은 `assertSame` 등 의도가 드러나는 assertion을 선택한다. 실행 중 예외가 없었다는 사실만으로 결과 검증을 대신하지 않는다.
- 종료 테스트는 제한 시간 내 실행 완료, 포트 재사용 등 종료 계약을 관찰한다. 출력 실패 후 재시도 금지처럼 횟수가 계약인 경우 호출 횟수도 확인한다.
- 버그 수정에는 원래 실패 조건을 재현하는 회귀 테스트를 추가한다. 주석만 변경하는 작업에는 별도의 동작 테스트를 추가할 필요가 없다.

## Tomcat 구현 근거와 프로젝트 정책

- 기능 테스트의 기대 동작은 `AGENTS.md`에 따른 작업 계획의 핵심 동작 대응·차이와 생략에서 도출한다. 계획에는 확인한 Tomcat 릴리스 태그 또는 SHA와 고정 소스 링크를 남긴다.
- 실제 Tomcat에서 확인한 동작과 학습 범위를 위한 프로젝트 정책을 구분한다. 프로젝트의 본문 미지원 501이나 연결당 한 요청 제한을 Tomcat 전체의 동작으로 설명하지 않는다.
- 새 차이를 테스트로 고정할 때는 이유·영향·검증 방법·후속 처리도 단계별 문서와 구현 제약 문서에 기록한다. 근거를 확인하지 못한 기대 결과를 Tomcat의 동작으로 단정하지 않는다.
- 지원 범위를 바꿀 때는 관련 테스트·주석·단계별 설명·`02-implementation-status.md`를 함께 갱신한다. 기존 테스트의 의미를 바꾸면서 과거 실행 기록까지 수정하지 않는다.

## 네트워크·동시성과 자원 정리

- 서버 포트는 `0`으로 바인딩하고 실제 할당된 포트를 사용한다. 특정 포트나 테스트 실행 환경의 외부 네트워크에 의존하지 않는다.
- 소켓 연결·읽기, `Future.get`, latch 대기에는 유한한 제한 시간을 둔다. 서버·동시성 테스트에는 `@Timeout`으로 전체 실행 시간도 제한한다.
- `Thread.sleep`으로 실행 순서를 추측하지 않는다. latch, Future, 프로토콜 이벤트 등 관찰 가능한 조건으로 동기화한다.
- 불완전한 요청에 대한 무응답처럼 대기 자체가 검증 대상일 때는 소켓 타임아웃을 사용할 수 있다. 그 조건과 이후 정상 처리·종료 등 확인하려는 결과를 주석에 적는다.
- 소켓·서버·Executor는 try-with-resources 또는 finally로 정리한다. assertion 실패 때도 서버가 닫히고 백그라운드 실행이 끝나도록 한다.
- 종료·연결 정리 책임을 검증하는 테스트에서는 테스트 측 정리가 검증 대상의 종료 실패를 가리지 않도록 실행 완료나 EOF 등을 먼저 확인한다.

## 실행과 완료 기준

저장소 루트에서 실행한다.

```powershell
# 수정한 대상의 테스트를 먼저 확인한다. 클래스 이름은 작업 대상에 맞게 바꾼다.
.\mvnw.cmd -B -Dtest=Http11ProcessorTest test

# 완료 전 전체 테스트·패키징을 검증한다.
.\mvnw.cmd -B clean verify
```

macOS·Linux에서는 `.\mvnw.cmd` 대신 `sh ./mvnw`를 사용한다.

- 주석 누락이 없는지 확인하고, 각 설명을 실제 assertion과 대조한다.
- 매개변수화 테스트는 메서드 수와 실행 사례 수가 다르므로 검증 기록에 둘을 혼동하지 않는다.
- 명령의 종료 코드와 `target/surefire-reports/`의 테스트 수·실패·오류·건너뜀을 확인한다. 성공을 추측해 기록하지 않는다.
- 기능 변경의 실행 증거는 해당 단계의 `doc/<단계>/` 문서에 날짜·명령·결과·검증 범위와 함께 추가한다. 과거 날짜와 결과를 덮어쓰지 않는다.
- 실행하지 못했거나 실패한 검증은 사유·관찰 결과·남은 확인 사항을 명시한다.

## 규칙 도입 시 검증 기록

2026-11-04에 테스트 파일 6개의 테스트 메서드 44개에 검증 목적 주석을 추가했다. 매개변수화 입력을 포함한 실행 사례는 76개다. 이번 변경은 주석과 작성 규칙 문서에 한정한다.

- 모든 테스트 실행 애너테이션 바로 위에 한국어 설명 주석이 있는지 검사했다. 44개 모두 확인했다.
- 처음 `clean verify` 실행은 세션 PATH에서 Windows PowerShell을 찾지 못해 Wrapper 시작에 실패했다. [빌드 환경의 세션 PATH 보정](../00-overview/03-build-environment.md)을 적용한 후 다시 실행했다.
- 재실행한 `.\mvnw.cmd -B clean verify`는 종료 코드 0·BUILD SUCCESS였다. 76개 실행, 실패·오류·건너뜀 각 0이며 JAR을 생성했다.
- 테스트 동작·입력·assertion은 변경하지 않았다. 과거 단계별 실행 기록은 그대로 보존한다.
