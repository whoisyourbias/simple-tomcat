# simple-tomcat 학습 가이드

최종 목표는 `simple-spring`에서 주문 한 건을 저장한 뒤 `GET /orders/count`를 보내면, 직접 만든 서버를 거쳐 상태 200과 본문 `1`을 받는 것이다.

## 요청 한 건의 여정

브라우저 → TCP 소켓 → HTTP 커넥터 → 서블릿 컨테이너 → simple-spring 디스패처 → 주문 컨트롤러. 응답은 역순으로 돌아가고 커넥터가 바이트를 소켓에 쓴다. 커넥터는 HTTP를 해석하고, 컨테이너는 서블릿을 선택해 호출하고, 디스패처는 컨트롤러 메서드를 선택한다. [Tomcat 아키텍처](https://tomcat.apache.org/tomcat-10.1-doc/architecture/overview.html) · [Spring MVC DispatcherServlet](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-servlet.html)

## 구현 순서

| 단계 | 직접 구현할 것 | 다음 단계로 넘어가는 기준 |
| --- | --- | --- |
| 1. 연결 한 개 | JDK의 `ServerSocket.accept()`로 연결을 받고 요청 헤더의 끝까지 읽은 뒤 고정 응답을 쓴다. 한 연결에서 요청 하나를 처리하고 `Connection: close`로 닫는다. | `curl.exe -v http://localhost:8080/hello`에서 상태 200과 본문을 확인한다. 요청을 다시 보내면 새 연결에서도 성공한다. |
| 2. HTTP 커넥터 | 요청 줄에서 메서드와 경로를 추출하고 헤더 끝의 빈 줄을 구분한다. 응답 상태 줄·헤더·본문을 쓰는 코드를 분리한다. 첫 범위는 본문 없는 GET이다. | 경로와 쿼리를 구분한다. 잘못된 요청 줄은 400으로 처리한다. 응답 본문이 `안녕`이면 UTF-8의 Content-Length는 6이다. |
| 3. 서블릿 컨테이너 | 경로에 서블릿을 등록하고 `init → service → destroy`를 구현한다. 요청마다 같은 서블릿 인스턴스를 호출하고 요청 객체는 새로 만든다. | 같은 서블릿에 두 번 요청하고 종료하면 호출 횟수가 1·2·1이다. 미등록 경로는 404, 서블릿 예외는 500이고 다음 요청은 성공한다. |
| 4. simple-spring 연동 | 서버를 라이브러리로 사용한다. 정확히 일치하는 경로를 먼저 찾고, 없으면 기본 서블릿으로 넘긴다. simple-spring이 디스패처를 기본 서블릿으로 등록하고 컨트롤러 경로를 관리한다. | 주문 한 건을 저장한 상태에서 실제 포트로 `GET /orders/count`를 보내 200과 `1`을 받는다. 모르는 경로는 디스패처를 거쳐 404가 된다. |
| 5. 동시성과 종료 | 1단계의 단일 스레드 서버에서 한 클라이언트가 헤더를 덜 보낸 채 기다리게 한다. 두 번째 요청의 지연을 관찰한 뒤 연결 수락과 처리를 분리하고 크기가 제한된 작업 풀과 읽기 타임아웃을 둔다. | 느린 연결이 열린 동안 다른 요청이 완료된다. 종료 시 새 연결 수락을 멈추고 작업을 정리한 뒤 서블릿을 해제한다. |

## 기존 프로젝트를 활용하는 법

이웃 저장소의 `minitomcat.MiniTomcat`에는 이미 단일 스레드 GET 처리, 정확한 경로 매핑, 서블릿 생명주기가 있다. 단계 1~3은 작은 예제를 직접 만든 뒤 기존 코드와 동작을 비교하는 데 쓴다. 단계 4에서 독립 라이브러리로 연결할 때 기존의 `addServlet`, `start`, `close` 사용법을 기준으로 삼는다. 기본 서블릿 매핑은 두 프로젝트를 연결하기 위해 추가할 기능이다.

첫 버전은 학습용 서블릿 인터페이스를 사용한다. 전체 Jakarta Servlet 호환, 다중 웹 애플리케이션 배포, keep-alive, NIO는 기본 연동을 확인한 뒤 각각 별도 실험으로 다룬다.
